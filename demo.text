## Office Management — Interview Notes (Full Project Flow)

This document explains the project end-to-end at a “core code” level, and gives you a clean way to describe it in an interview.

---

## 1) What this project is

**Office Management** is a full-stack web application:
- **Frontend**: React (Vite) in `client/`
- **Backend**: Node.js + Express REST API in `server/`
- **Database**: MongoDB

It supports two main user experiences:
- **Employee**: request leave + view own leave requests
- **Admin/Manager**: manage departments/employees + approve/deny leave requests

---

## 2) Folder layout (mental map)

### Frontend (`client/`)
- `src/main.jsx`: app bootstrap (Router + Auth + Redux store)
- `src/App.jsx`: route table and role-based route splitting
- `src/components/ProtectedRoute.jsx`: route guard (requires auth + optional allowed roles)
- `src/components/OfficeLayout.jsx`: app shell + sidebar that changes by role
- `src/state/auth.jsx`: **Auth Context** (token, user, login/logout, boot from localStorage)
- `src/lib/api.js`: axios instance + API base URL resolver
- `src/store/store.js`: Redux store (RTK Query)
- `src/store/officeApi.js`: **RTK Query API slice** (departments/employees/leaves/health)
- `src/pages/*`: screens

### Backend (`server/`)
- `src/index.js`: Express app entry, CORS, JSON middleware, routes mounted under `/api/*`
- `src/routes/*.routes.js`: resource-based REST endpoints
- `src/middleware/auth.js`: JWT auth middleware (`requireAuth`)
- `src/lib/jwt.js`: JWT signing/verification helpers
- `src/lib/db.js`: MongoDB connection
- `src/models/*`: Mongo models/helpers (User/Employee/Department/LeaveRequest)

## 3) Total flow of the project (end-to-end)

### Step A — User opens the site (client)
1. Browser loads the SPA from Vite (dev) or `client/dist` (build).
2. `client/src/main.jsx` renders the app and wraps it with:
   - `BrowserRouter` (routing)
   - `AuthProvider` (auth context)
   - Redux `<Provider store={store}>` (RTK Query store)

### Step B — Auth boot (token persistence)
1. `AuthProvider` in `client/src/state/auth.jsx`:
   - Reads `om_token` + `om_user` from `localStorage`
   - Sets axios Authorization header using `setAuthToken(token)`
   - If a token exists, calls `GET /api/auth/me` to validate and refresh user
2. That makes refresh/reopen work: the app restores the session automatically.

### Step C — Login (Landing page with 2 portals)
1. User logs in from `client/src/pages/Landing.jsx` using one of two panels:
   - **Employee Access** (only employees allowed)
   - **Administrator Access** (only admin/manager allowed)
2. Both call the same auth method: `login(email, password)` which hits:
   - `POST /api/auth/login` (server)
3. After login succeeds, the landing page enforces portal rules:
   - If someone signs in on the wrong panel, the app calls `logout()` and shows a clear message.

### Step D — Protected routing (role-based)
1. After login, user is routed to `/app`.
2. `client/src/App.jsx` uses `ProtectedRoute` to ensure:
   - user is authenticated
   - and optionally has one of the required roles for that route tree
3. App splits into two route trees:
   - `/app/employee/*` for role `employee`
   - `/app/admin/*` for roles `admin` and `manager`
4. `OfficeLayout` also changes the sidebar items depending on role.

### Step E — Data fetching (business data)

There are two “API layers” on the client:

1) **Auth (Context + axios)**
- Auth is kept in `client/src/state/auth.jsx`
- Uses the axios instance from `client/src/lib/api.js`
- Endpoints used:
  - `POST /api/auth/login` (gets token + user)
  - `GET /api/auth/me` (boot/validate token)

2) **Server-state (Redux Toolkit Query)**
- Business resources use RTK Query in `client/src/store/officeApi.js`
- `fetchBaseQuery` automatically attaches JWT by reading `om_token` from `localStorage` in `prepareHeaders()`
- Pages call generated hooks such as:
  - `useGetDepartmentsQuery`, `useCreateDepartmentMutation`, `useDeleteDepartmentMutation`
  - `useGetEmployeesQuery`, `useCreateEmployeeWithUserMutation`, `useDeleteEmployeeMutation`
  - `useGetMyLeavesQuery`, `useCreateLeaveMutation`
  - `useGetAllLeavesQuery`, `useUpdateLeaveStatusMutation`

RTK Query is used mainly because this data is **server-state**: it benefits from caching, consistent loading/error handling, and predictable refresh after mutations.

### Step F — Backend processing (Express)
1. API entry is `server/src/index.js`.
2. Routes are mounted under:
   - `/api/auth`
   - `/api/departments`
   - `/api/employees`
   - `/api/leaves`
3. Protected routes use JWT middleware (`requireAuth`) to verify:
   - `Authorization: Bearer <token>`
   - token validity and user identity

### Step G — Database (MongoDB)
- MongoDB stores users and business entities (departments, employees, leave requests).
- API handlers read/write documents and return JSON responses consumed by the client.

## 4) Where Redux is used (exact files) and why

### Where (files)
- `client/src/main.jsx`
  - Adds `<Provider store={store}>` so the app can use Redux hooks.
- `client/src/store/store.js`
  - Configures the store and registers RTK Query reducer + middleware.
- `client/src/store/officeApi.js`
  - Central place for API endpoints and cache tags.
- Pages using RTK Query hooks:
  - `client/src/pages/Dashboard.jsx` (health)
  - `client/src/pages/Departments.jsx` (departments)
  - `client/src/pages/Employees.jsx` (employees + departments dropdown)
  - `client/src/pages/EmployeeLeaves.jsx` (my leaves)
  - `client/src/pages/AdminLeaves.jsx` (all leaves + status update)

### Why (interview-ready)
Redux is used **only for server-state**, via RTK Query.

What RTK Query gives you:
- **Caching**: avoid refetching the same lists on every navigation.
- **Consistency**: standardized `data / isLoading / isError / error`.
- **Auto refresh after writes**: “tag invalidation” refreshes lists after create/delete/update.
- **Less boilerplate**: no repetitive `useEffect + useState + api.get/post` in every page.

Auth is intentionally left in **Context** because it’s small and app-wide; RTK Query is used for heavier, shared resource data.

## 5) Role flow and access rules (how to explain)

### UI entry points
- Landing has **two sign-in panels**:
  - Employee Access → employee only
  - Administrator Access → admin/manager only

### Route protection
- `ProtectedRoute` enforces:
  - authenticated session
  - role matches when a route subtree declares allowed roles

### Backend is the real security
- Frontend routing/menus are UX.
- Backend authorization is what prevents forbidden actions if someone tries to call APIs directly.

## 6) Best 60–90 second interview answer (script)

“This is a full-stack office management app: React/Vite client, Express REST API server, MongoDB for persistence. Authentication is JWT-based: login returns a token, the client stores it and sends it as a Bearer token, and the server protects routes via middleware that verifies the token. The UI is role-based: employees can request leaves and view their requests, while admins/managers can manage departments and employees and approve or deny leaves. For state, auth is handled with a React Context because it’s lightweight, but I use Redux Toolkit Query for server data like departments, employees, and leaves to get caching, consistent loading/error states, and automatic refetch using tag invalidation after mutations.”

## 7) Common follow-up questions (quick answers)

### Q: Why not use Redux for auth too?
A: Auth is small and changes infrequently; Context is simpler. RTK Query is a better fit for large, shared, cacheable server-state.

### Q: How do you keep data fresh after a create/delete?
A: RTK Query invalidates tags (for example `Department:LIST`) so dependent queries refetch automatically.

### Q: What happens on refresh?
A: The token/user are in `localStorage`. On boot, the app calls `/api/auth/me` to validate the token and restore the session.
